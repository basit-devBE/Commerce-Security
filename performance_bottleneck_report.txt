Performance Bottleneck Analysis Report
Epic 1 - User Story 1.1
Commerce Backend Application
Date: February 26, 2026

1. Overview
This report documents the performance bottleneck analysis conducted on the Commerce Backend application as part of Epic 1, User Story 1.1. The objective was to identify where performance bottlenecks exist in the secured backend, record baseline metrics, and implement targeted optimizations.

Profiling Tool Used: VisualVM (primary) and IntelliJ Built-in Profiler (verification)
Application: com.example.commerce.CommerceApplication
Server Port: 8080
Framework: Spring Boot with Spring Security (JWT-based authentication)

4. Root Cause Analysis
4.1 Bottleneck 1 - Repeated JWT Token Parsing
In the original JwtAuthenticationFilter, the JWT token was being parsed four separate times per request:

validateAccessToken(token)          ? extractAllClaims(token, accesssecretKey)
extractUserIdFromAccessToken(token)  ? extractAllClaims(token, accesssecretKey)
extractEmailFromAccessToken(token)   ? extractAllClaims(token, accesssecretKey)
extractRoleFromAccessToken(token)    ? extractAllClaims(token, accesssecretKey)

Each of these method calls independently invoked extractAllClaims, which performs a full cryptographic JWT parse and signature verification. This meant the same token was being fully decoded and verified four times on every single request.

4.2 Bottleneck 2 - SecretKey Rebuilt on Every Request
The getKey() method in JwtService was reconstructing the SecretKey object on every call:

private SecretKey getKey(String secretKey) {
    return Keys.hmacShaKeyFor(secretKey.getBytes(StandardCharsets.UTF_8));
}

Keys.hmacShaKeyFor() is a cryptographic operation that should only be performed once at application startup. Calling it on every request added unnecessary overhead and was confirmed by the profiler showing getAccessSecretKey() taking 304ms in later runs.

4.3 Bottleneck 3 - Large Waiting Time Gap
The significant gap between Total Time and CPU Time (e.g. 389ms total vs 38.7ms CPU in exec-9) indicated blocking wait time. Investigation of the TokenBlacklistService confirmed the isBlacklisted check uses a ConcurrentHashMap.containsKey() which is O(1) and not the source of the waiting. The waiting time is attributed to Spring Security's downstream filter chain processing and actual endpoint business logic executing after the JWT filter.

5. Optimisations Applied
5.1 Fix 1 - Single Token Parse in the Filter
The filter was updated to call extractAllAccessClaims once and reuse the resulting Claims object for all subsequent data extraction:

Claims claims;
try {
    claims = jwtService.extractAllAccessClaims(token);
    if (claims.getExpiration().before(new Date())) {
        filterChain.doFilter(request, response);
        return;
    }
} catch (JwtException e) {
    filterChain.doFilter(request, response);
    return;
}
Long userId = claims.get("userId", Long.class);
String email = claims.getSubject();
String role  = claims.get("role", String.class);

This reduced JWT parses from 4 per request down to 1.

5.2 Fix 2 - Cached SecretKey Using @PostConstruct
The JwtService was updated to build the SecretKey objects once at application startup using @PostConstruct, storing them as instance fields:

private SecretKey cachedAccessKey;
private SecretKey cachedRefreshKey;

@PostConstruct
public void init() {
    this.cachedAccessKey  = Keys.hmacShaKeyFor(accessSecretKey.getBytes(StandardCharsets.UTF_8));
    this.cachedRefreshKey = Keys.hmacShaKeyFor(refreshSecretKey.getBytes(StandardCharsets.UTF_8));
}

All methods in JwtService were updated to use cachedAccessKey and cachedRefreshKey directly instead of calling getKey() on every invocation. A dedicated extractAllAccessClaims(String token) method was added that uses the cached key, removing the need to pass the secret key string as a parameter from outside the service.
